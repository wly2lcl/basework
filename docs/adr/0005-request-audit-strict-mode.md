# ADR 0005: 请求审计的兼容模式与严格模式

- Status: Accepted
- Date: 2026-09-12
- 关联任务：REL-004

## 背景

`request.built` 事件承载「模型看到的请求 == 日志记录的请求」这个不变量：它记录
条数、指纹与来源片段。但历史实现把它当作尽力而为的记录——写入失败只打一行日志，
然后照常把请求发给 Provider。

这留下一个事后无法分辨的缺口。看到日志里没有某次请求的记录时，有两种可能：

1. 那次请求因为跨进程重启、进程崩溃、压缩等原因**没被记录**；
2. 那次请求**根本没有发出**。

两种情况在日志上完全一样。也就是说，这个「不变量」在最需要它的时候——审计记录
缺失的时候——无法给出结论。压缩会把早期日志折叠、写盘会因为磁盘满而失败，
所以这个缺口不是理论问题。

同时，改动不能破坏既有嵌入调用：它们没有为审计失败准备错误路径，把默认行为直接
换成「审计失败就中断对话」会让它们的对话无故失败。

## 决定

引入 `AuditMode`，两种取值：

- **compatible（默认）**：审计写入失败只记日志并继续发送请求。保持了历史行为，
  既有嵌入调用不受影响。代价是上述缺口继续存在。
- **strict（可选）**：审计写入失败时，在发出**任何** Provider 调用之前中断本轮，
  返回带阶段与来源的 `AuditError`。于是「日志里没有 request.built」严格等价于
  「没有发出过请求」。

策略通过可选接口 `AuditPolicyProvider` 从 `TurnD` 取，而不是给 `TurnD` 增加必选
方法——后者会破坏所有外部实现。未实现该接口时按 compatible 工作。

触发方式：`agent.WithAuditMode(...)`，CLI 侧由 `BASEWORK_AUDIT_MODE=strict` 接入。
取值非法时明确报错，不静默回落。

## 审计边界

指纹**覆盖**哪些内容、哪些内容**可以仅凭日志重建**，是两件不同的事。写进代码
（`agent.AuditBoundaries()`）而不是只写在文档里，避免有人把正常差异当漂移去修：

| 内容 | 被指纹覆盖 | 可由日志重建 | 说明 |
|---|---|---|---|
| 事件日志投影出的 messages | 是 | 是 | system prompt、steering、历史都来自事件日志 |
| hook 改写后的 messages | 是 | **否** | 指纹在 `RunBeforeLLM` 之后算，改写结果被记入；但 hook 是调用方代码、不在日志里 |
| 工具定义快照 | 是 | **否** | 工具定义来自注册表，日志只留 `ToolCount` 与它们对哈希的贡献 |
| Provider 传输层变换 | **否** | 否 | 指纹算在交给 `llm.Request` 那一刻；此后各家适配器的协议改写不在范围内 |
| 助手回复与工具结果 | 否 | 否 | 发生在请求之后，核对时必须把日志截回请求那一刻 |

推论：核对请求必须 (a) 传入当时实际使用的同一份工具定义，(b) 按该请求自己的 Seq
把日志截回去。`BenchmarkRequestBuilt` 式的「拿最终日志比对」在任何多轮会话里都会
失败，那不是漂移，是核对方法错了。

## 后果

- 严格模式下可用性换可审计性：磁盘写入故障会让对话失败，但失败是显式且可定位的
  （错误里带阶段、来源、session）。
- compatible 仍是默认值，因此本次改动不改变任何现有部署的行为。
- 请求重建与校验从测试专用工具变成运行时 API（`RebuildRequestAt`、`VerifyRequestBuilt`、
  `RequestBuiltSeqs`），便于在诊断与后续任务（CTX-002/003）中复用。
- 装了改写请求的 hook 时，`VerifyRequestBuilt` 必然报错——这是设计，不是缺陷。
