# ADR 0001: 用轻量 ADR 记录架构决策

- Status: Accepted
- Date: 2026-09-12
- Supersedes: —

## 背景

basework 此前用 `openspec/` 承载设计意图，共 160 个文件。它的问题不是「记录决策」这件事本身，而是流程重量：一次改动要先写提案、再走评审状态机，且内容与代码没有任何强制关联。结果是目录越堆越大、维护成本高于收益，最终被整体删除——**连同「决策留痕」这个真正有价值的部分一起丢了**。

对照项目 deepseek-harness 有约 2,945 篇决策记录（`.agents/notes`），其价值不在数量，而在「为什么这么改」在代码之外有处可查。而 basework 的 CHANGELOG 只记录「改了什么」，不记录「否决过什么方案、为什么」。

于是出现一个具体问题：`pkg/tool/builtin` 反向依赖 `internal/` 这件事，修复时明明有多个可选方案（复用 `pkg/agent` 接口 / 新建共享接口包 / 各自定义），最终选了哪一个、为什么——如果没有落点，半年后重看代码的人（包括作者自己）无从判断，很可能重新引入同类问题。

## 决定

采用 ADR（Architecture Decision Record），但只保留骨架：

- 位置 `docs/adr/`，命名 `NNNN-kebab-title.md`，四位递增序号
- 每篇**只允许三节**：`## 背景` / `## 决定` / `## 后果`
- 头部一个 `Status` 字段：`Proposed | Accepted | Deprecated | Superseded`
- 不做审批链、不做状态机、除「结构校验」外不做任何流程

配套由 `scripts/doccheck` 校验（文件名格式、三节齐备、Status 合法），接入 `make check-docs` 与 CI 的 `quality` job。

## 后果

正面：
- 「为什么否决了另一个方案」有了固定落点，不必从 git log 里考古
- 校验交给机器，人只写内容；不会因为漏了某一节而被流程卡住
- 三节结构天然抑制长篇大论：想写第 4 节就得先想清楚它是不是属于 CHANGELOG

代价与后续：
- 序号需人工递增，不引入自动分配（避免为此维护一个状态文件）
- 需要自律：不是每个改动都值得写 ADR，只有「存在被否决的替代方案」时才写
- 与实施方案的分工必须保持清晰：ADR 记「已定的决策」；按 ADR 0004，现行实施方案在 `docs/tasks/`，历史 plans 已归档。分工一旦模糊，ADR 就会退化成第二个 openspec
