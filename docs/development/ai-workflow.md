# 交给 AI 开发的操作说明

## 每次只交付一个明确任务

适合上下文较短、推理能力较弱的 AI：不要让它一次“完善整个项目”。给它一个任务 ID、对应任务卡和需要遵守的边界即可。任务本身较大时，先按卡片步骤做一个小切片，验证后再继续；整个任务验收前保持进行中。

推荐阅读顺序：`docs/README.md` → `docs/STATUS.md` → `docs/TASKS.md` 对应行 → 对应任务卡 → 涉及的包契约 → 必要源码和测试。无需每次通读 archive。

## 可直接复制的开发指令

```text
请完成 Basework 的任务 <任务 ID>。
1. 阅读 docs/README.md、docs/STATUS.md、docs/TASKS.md 中该任务及链接的任务卡。
2. 检查依赖是否完成；读取 git status 和相关差异，保留已有未提交改动。
3. 对照实际代码确认缺口，列出本次会修改的少量文件和验收步骤；不要重做已有实现。
4. 将该任务标为进行中，填负责人；按任务卡的小步骤实现，保持 pkg 不依赖 internal、internal 不依赖 cmd。
5. 用失败场景/边界测试证明修复；保持默认与 sqlite memory 构建兼容。
6. 执行针对性检查；涉及代码时运行 make gen，最后 make check-docs 和 make check-arch。
7. 保存 docs/development/evidence/<任务 ID>.md，记录具体修改、测试命令、结果、环境、未验证内容。
8. 只有全部验收条件满足时标为完成；代码写完但缺真实验证则标待验证；无法继续则标阻塞并说明解除条件。
9. 更新受影响的使用指南、包契约和当前状态。报告本次完成内容、证据路径和下一项。
只处理该任务。不要自动提交、推送、发布或改动其他任务的行为。
```

## 实施中的固定边界

- 不凭记忆猜接口：先找现有定义与调用方；不存在的路径可能是任务卡中明确规划的新增目录。
- 不通过删测试、禁用工具、放宽权限或隐藏错误来“通过”验收。
- 接口属于 `pkg/` 时优先新增可选 Option/小接口；改变持久化语义需要迁移、兼容测试和 ADR。
- UI 回调只投递消息，状态修改在事件循环；长任务要有 owner、取消、输出限额与清理路径。
- 发现卡片前提已经变化，先记录证据并修订卡片；不要按过时计划硬改。
- 遇到失败先检查环境和既有基线；没有凭证时不伪造真实模型结果。

## 复审任务的执行要求

1. 先读原证据顶部的复审说明、对应 A/B 编号与复现代码；历史“完成”结论不能覆盖后来的失败复现。
2. 把对应失败复现转为正式回归测试，确认修复前确实失败；涉及入口接线时，用真实 runtime/CLI/TUI 验证，不能只数 helper 的选项或手工种数据。
3. 修复后运行定向测试与相关门禁，记录实际 commit / 工作区差异及可保留的脱敏输出。
4. 卡片原验收和复审补充必须同时满足；不能通过删测试、放宽断言、把“产品恢复”改叫“存储投影”来关闭任务。
5. 依赖回退的任务可以保留已通过的局部证据，等待前置重新验收；不要把依赖回退误当成要求重写整个模块。

## 交接模板

```text
任务 ID：
当前状态：进行中 / 待验证 / 阻塞
已完成的小步骤：
修改文件与原因：
已运行检查与结果：
未验证项和所需条件：
下一步从哪个文件/测试继续：
不要重复执行的动作：
证据文件：
```

把交接写入同一任务证据文件的“剩余与交接”部分，看板只保留链接。换 AI 时让它先读这份记录。

## 用户如何看进度

打开 [TASKS](../TASKS.md) 看状态，或运行 `make progress` 看各阶段数量。点证据链接判断完成质量；尤其检查真实模型、人工 TUI 与平台验证是否确实执行。复审阶段先按看板的 P1/P2 执行顺序继续已重开的任务，再领取新待办；一次只做一个有明确验收的小任务。候选长期方向不自动执行。
