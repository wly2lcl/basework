# 验证与完成规则

## 验证层次

| 类型 | 能证明什么 | 不能替代什么 |
|---|---|---|
| 静态/文档检查 | 结构、引用、依赖边界有效 | 业务是否可用 |
| 单元/协议重放 | 已覆盖条件下的逻辑行为 | 外部真实模型兼容性 |
| 本地集成 | 指定入口、组件和环境可协作 | 跨平台和干净安装 |
| 真实 Provider | 指定模型/日期/端点的实际流程 | 其他模型或未来服务版本 |
| 人工体验 | 用户能完成操作与理解状态 | 全部边界条件和并发正确性 |

## 按变更选择检查

文档整理：`make check-docs`、`make progress`、`git diff --check`。检查器变化要验证成功路径和故意损坏的布局/依赖/链接/证据会被拒绝。

业务代码：先跑任务卡指定包的测试，再跑默认与完整 tag 构建相关检查；涉及生命周期、事件与共享状态时跑对应 race 测试。新增生成器/检查脚本后也运行 `make gen` 并确认输出重复生成一致。

```bash
make check-docs
make check-arch
go test ./... -count=1
go test -tags "sqlite memory" ./... -count=1
go vet -tags "sqlite memory" ./...
go build -tags "sqlite memory" ./cmd/basework
make gen
```

根据变更涉及的并发范围执行 `go test -race`。CI 的准确检查范围以 `.github/workflows/build.yml` 为准；本地执行不等于 CI 已通过。

## 真实场景记录

测试项目使用独立目录，不把产品代码仓库当破坏性验证样本。记录 Provider、model ID、端点类别（脱敏）、测试日期、输入、工具轨迹、实际测试退出码、失败/重试次数、耗时。认证/模型能力未知时停止该场景，记录原因。

任务要求连续次数或平台矩阵时必须全部满足；缺少其中一项保持待验证或阻塞。不要用平均结果掩盖失败，也不要把未运行写成跳过后通过。

## 发布门槛

正式发布候选必须具备：相关本地检查、候选 commit 的跨平台 CI、打包 dry-run、真实模型场景、人工 TUI 流程、声明平台的安装/升级结果及已知问题清单。未验证的平台不宣称支持已验证。创建发布报告不代表获准发布；按用户的发布指令操作。

## 证据格式

从 [证据模板](evidence/TEMPLATE.md) 复制为任务 ID 对应文件。自动检查只能确认字段和文件存在；评审人仍需核对结果是否足以支撑任务验收。
