## 变更

**新增**

- `pkg/config/provider_endpoint.go`：`ProviderEndpoint` 类型、`Config.Providers` 载体、
  `ProviderEndpointFor` / `EffectiveProviderName` / `ResolveEndpoint` / `ValidateBaseURL` /
  `DisplayURL` / `validateProviderEndpoints`。解析是纯函数（环境值由调用方注入），
  使 runtime 与 `config explain` 可以复现同一结果。
- `docs/adr/0007-custom-provider-endpoint.md`：载体、优先级链、同源冲突与「不静默回落」的决策。

**修改**

- `pkg/config/config.go`：`Providers` 字段；`clone()` 深拷贝该 map；`Validate()` 接入端点形态校验。
- `cmd/basework/runtime.go`：解析生效端点并**真的传给** `provider.Create`（`BaseURL` + 覆盖来源的形态校验）。
- `cmd/basework/agent.go`：新增 `endpointLabel`；`providerAPIKey` 纳入 `providers.<name>.api_key`；
  `buildProviderOptions` 接收解析结果，`ollama` 在有 provider 级端点时不再下发旧的 `ollama.endpoint`（ADR 0007 的同源冲突规则）。
- `cmd/basework/config.go`：`configHasKey` 纳入 provider 级 key；explain 新增「生效端点」来源展示与
  `BASEWORK_BASE_URL` 覆盖行；`openai-compat` 无端点时给出启动会失败的提示。
- 文档：`docs/guides/cli-guide.md`（虚构 schema 改为真实 schema）、`docs/guides/configuration.md`
  （新增 `providers` 字段与「自定义端点」小节）、`docs/reference/pkg/config.md`（包契约与 Known Limitations）。

**范围外未做**（保持卡片边界）：未改任何 Provider 的默认端点常量，未改权限默认值，
未引入第三方依赖，未新增 per-provider 环境变量别名（如 `OPENAI_BASE_URL`，已在 ADR 0007 的「后续」中登记）。

**顺带修掉的文档失真**（同一文件、同一类问题，避免留着继续误导）：`cli-guide.md` 的环境变量表里
`COHERE_API_KEY`、`MISTRAL_API_KEY`、`GROQ_API_KEY`、`DEEPSEEK_API_KEY`、`TOGETHER_API_KEY`、
`AZURE_OPENAI_API_KEY`（代码读的是 `AZURE_API_KEY`）、`BASEWORK_CONFIG`、`BASEWORK_LOG_LEVEL`
代码从未读取；`configuration.md` 声称存在 `.basework/config.json` 项目级配置，但 `Discover()` 只认 `config.json`。
两处均已按代码实际行为更正，并把「实际读取的全部环境变量」用一次全仓 `os.Getenv` 检索核对过。

**3. 真实二进制的端到端证明**（`/private/tmp/rel-003`，隔离 `HOME`，key 只经环境变量传入，不落盘）：

正向——配置 `providers.openai.base_url = https://newapi.doubb.top/v1`（key 走 `OPENAI_API_KEY`），
在隔离项目上跑 CLI 单次编排，场景为「读 `calc.go`/`calc_test.go` → 修 `Add` → 跑 `go test`」：

| run | CLI 退出码 | 耗时(s) | 轮数 | 工具调用 | 其中失败 | 独立复核 `go test` 退出码 |
|---|---|---|---|---|---|---|
| CLI-1 | 0 | 41 | 10 | 17 | 6 | 0 |
| CLI-2 | 0 | 41 | 11 | 18 | 8 | 0 |
| CLI-3 | 0 | 12 | 6 | 11 | 3 | 0 |

3/3 全部完成闭环并改对了文件；每次运行前把 `calc.go` 重置为缺陷态（`go test` 退出码 1）。
工具轨迹里的失败全部是模型先猜 `/home/user/calc.go` 再自我纠正，无一例是协议或装配层错误。
`go test` 退出码由夹具在 CLI 进程结束后**独立执行**得到，不采信模型自述。

反向对照（同一个真实二进制、同一条命令，只把 `base_url` 换成不可达的 `http://127.0.0.1:1/v1`）：

```
Error: 处理消息失败: [network] request failed: Post "http://127.0.0.1:1/v1/chat/completions": dial tcp 127.0.0.1:1: connect: connection refused (status=0)
```

与基线段落里那次 `[auth] authentication failed (status=401)` 形成对照：同一种实验，改动前请求打到
默认端点所以表现为鉴权失败，改动后错误直接指向配置的端点。这是「不静默回落」最直接的证据。

`config explain` 的实际输出（key 已脱敏，端点来源可见）：

```
环境覆盖:
  BASEWORK_BASE_URL 未设置 → 生效端点取配置文件 providers.<provider>.base_url

自定义模型端点:
  生效 base_url: https://newapi.doubb.top/v1
  来源: 配置文件 providers.openai.base_url
```
