# UI-002 权限与编辑确认体验

## 基线

- 前置：UI-001、EDIT-003 均已完成（看板 22/28）。
- 已有能力：`permission.Checker` 交互模式含 `PromptFunc` 钩子（CLI 终端问答已接 `newRuntimePermissionPrompt`）；`edit_files` 提交前重新校验基线与权限（EDIT-002/EDIT-003）；TUI 有 `dialog.Manager`/`ConfirmDialog` 组件。
- 缺口：审批交互只有 CLI 终端问答；TUI 无图形审批；无带 ID 的请求协议（无超时、无陈旧应答防护）。

## 变更

- `internal/permission/approval.go`（新增）：
  - `ApprovalRequest`（唯一 ID + 工具名 + 目的 + 路径 + diff 预览 + 风险依据）；
  - `ApprovalBroker`：`Request`（生成 ID、登记 pending、通知 UI、等待应答）、`Respond`（按 ID 应答，未命中返回 false）、`Close`（pending 全部以 Closed 结局）；超时/关闭等价拒绝；
  - `ApprovalPromptFunc`：把 broker 适配成 `PromptFunc`；**决策刻意不缓存**——「批准不会错误应用到下一请求」由「唯一 ID 隔离 + 不缓存」双重保证；
  - `BuildApprovalRequest`：从参数提取目的/路径/diff（2KB 截断）/风险依据（rm、git push、sudo 等危险特征 → 中文风险说明；支持调用方注入敏感路径检查结果）。
- `internal/tui/dialog/approval.go`（新增）：`ApprovalDialog`，展示工具/目的/路径/风险/预览，键盘完成全部操作（y=允许；n/esc=关闭，均等价拒绝；上下键滚动预览）；`CloseDialogMsg` 导出供对话框自我关闭（Manager 消费移除栈顶）。
- `internal/tui/app.go`：`ApprovalRequestMsg`（携带 ID 与 `Respond` 闭包）→ 打开模态审批对话框；`tea.Tick` 超时自动拒绝关窗（与 broker 超时双保险，幂等）；同时只允许一个审批窗口（防御性拒绝并发请求）。
- `cmd/basework/runtime.go`：`newPermissionChecker` 增加 prompt 覆盖参数；`runtimeAgentOptions.ApprovalPrompt`。
- `cmd/basework/tui.go`：TUI 模式构造 `ApprovalBroker`、注入 `ApprovalPromptFunc`、`forwardApprovalRequests` 把请求转成 TUI 消息（`Respond` 闭包按 ID 回投）；CLI 保持终端问答。
- 测试：`internal/permission/approval_test.go`（6 条）、`internal/tui/dialog/approval_test.go`（3 条）、`internal/tui` App 级审批流（1 条）。

## 验证

- 任务卡针对性验证：`go test -race ./internal/tui ./internal/permission ./cmd/basework -count=1` → **三包全 ok**。
- 验收条件逐条：
  - **拒绝/关闭后不执行操作**：拒绝走 `Checker.Check` 返回 false → pipeline 不执行该工具调用（既有链路）；broker 层超时/关闭/Closed 均不放行（`TestApprovalBroker_TimeoutIsDenial`、`TestApprovalBroker_CloseCancelsPending`）。
  - **批准不会错误应用到下一请求**：`TestApprovalBroker_StaleApprovalDoesNotLeak`（过期请求的迟到批准被忽略，新请求需新应答）+ 决策不缓存 + App 级 `TestApp_Update_ApprovalFlowIsolated`（相同工具的第二个请求重新弹窗）。
  - **对比结果与实际文件一致且键盘可完成操作**：diff 预览来自实际参数（edit_files 的 edits 序列化、bash 命令原文）；提交仍走工具自身基线校验（edit_files Prepare/Commit 重新哈希比对，EDIT-002 已建立）；键盘 y/n/esc 全流程（`TestApprovalDialog_KeysCompleteFlow`）。
  - 展示一致性：`TestApprovalDialog_ViewShowsEvidence`、`TestBuildApprovalRequest`。
- 全量：双模式 34/34 包全绿（退出码 0）；`GOOS=windows`/`GOOS=linux` 交叉编译通过；`make check-arch`/`check-docs` 通过；`make gen` 幂等。
- race 过程中抓到测试自身的数据竞争（notifier 回调写共享变量）→ 已加锁修复，产品代码无竞争。

## 剩余与交接

- **人工实测边界**：全屏 TUI 下真实击键的弹窗体验（视觉布局、滚动手感）无法在本环境验证（无 TTY），留待 SHIP-001 实机验收；键盘语义与关闭/拒绝等价性已由单元测试覆盖。
- `cacheDecision` 刻意恒为 false：想要「永久允许」应走权限规则（ask→allow 持久化），而不是让单次批准悄悄变成全局豁免。
- UI-003（未开始）依赖本任务。

## 结论

UI-002 完成。审批请求成为带唯一 ID 的 UI 事件，展示目的/路径/diff/风险依据，允许/拒绝/关闭/超时全键盘可达，拒绝与关闭绝不执行操作，批准被 ID 隔离且不缓存、不会错误应用到下一请求；确认后的提交仍受工具层基线与权限校验约束。
