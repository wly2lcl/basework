## 变更

**本任务没有产品代码变更。** 新增的都是工作区外的验证物，不进入仓库：

- 闭环夹具（独立 Go 模块，`replace` 指向本地 basework）：用可嵌入 API 驱动一轮完整闭环——
  `provider.Create(provider.Config{Type, APIKey, BaseURL, ModelID})` +
  `agent.New(WithModel, WithSystemPrompt, WithTools(builtin.All()...), WithMaxSteps, WithCallback)` +
  `HandleMessage`。夹具记录工具轨迹、**由夹具在 agent 结束后独立执行 `go test ./...` 得到的真实退出码**、耗时与 token 用量。
- 隔离项目与 6 次原始运行记录（JSON）。

**为什么证据来自可嵌入 API 而不是 CLI**——这是本次新发现的阻塞点：

`cmd/basework` 的 `newRuntimeAgent` 调用 `provider.Create` 时**从不设置 `Config.BaseURL`**；
全仓库非测试代码中 `BaseURL:` 的赋值是 **0 处**。配置文件同样没有 `base_url` 字段。
`docs/guides/cli-guide.md` 里那套 `providers.<name>.base_url` 是**不存在的 schema**。

实测（用无效 key，避免把真 key 发给第三方）：把该 schema 写进 `--config` 指定的文件、并把
`base_url` 指向不可达的 `http://127.0.0.1:1/v1`，运行 `basework agent -m "..."` 得到：

```
Error: 处理消息失败: [auth] authentication failed (status=401)
```

若是 `base_url` 生效，错误应当是连接失败（`127.0.0.1:1` 不可达），而不是一个 HTTP 401——
说明请求实际打到了默认端点，**配置被静默忽略**。因此 CLI 目前不满足卡片"已配置的端点"这一前提。

## 验证

场景固定：读 `calc.go` → 修 `Add` → 运行 `go test` → 解释结果。
每次运行前把 `calc.go` 重置为缺陷态并 `go clean -testcache`，确保退出码不是缓存结果。

| run | 协议 | 闭环通过 | go test 退出码 | 文件确实被改 | 耗时(s) | token | 工具步数 | 失败的工具调用 |
|---|---|---|---|---|---|---|---|---|
| A1 | openai-compat | 是 | 0 | 是 | 11.7 | 2260 | 13 | 3 |
| A2 | openai-compat | 是 | 0 | 是 | 3.2 | 1547 | 5 | 0 |
| A3 | openai-compat | 是 | 0 | 是 | 5.7 | 1984 | 9 | 2 |
| B1 | anthropic | 是 | 0 | 是 | 5.8 | 874 | 9 | 2 |
| B2 | anthropic | 是 | 0 | 是 | 3.1 | 527 | 4 | 0 |
| B3 | anthropic | 是 | 0 | 是 | 17.8 | 554 | 4 | 0 |

**两协议各连续 3 次，6/6 完成闭环**；`go test` 真实退出码 6 次全为 0，且都以退出码 1 的缺陷态为起点。

**失败与重试（按卡片要求，不只记成功样本）**：6 次共 7 次工具调用失败，全部是模型**自己猜路径**
引起的自我纠正，无一例是代码/协议层错误：

- A1：模型先断言工作目录是 `/home/user/project/`（不存在），连续 3 次失败（2×read + 1×bash），
  随后用 `pwd`、`ls` 探到真实路径并恢复，最终 13 步完成。
- A3、B1：各有 2 次 `read` 因同样原因失败后恢复。
- 未出现整轮失败、未出现需要人工重试的样本；未出现参数重复拼接、tool_call ID 错配、
  或失败后重复执行有副作用的工具。

**模型输出与真实退出码分开记录**：`final_text` 是模型自述（可能不准）；
`test_exit_code` 由夹具独立执行 `go test ./...` 得出，不采信模型自述。

### 产品层（CLI）路径：CFG-004 修复后补跑，3/3 通过

CFG-004 落地后，用**同一个真实端点、同一场景**改走 CLI 单次编排路径

每次运行前把 `calc.go` 重置为缺陷态（`go test` 退出码 1）并清测试缓存：

| run | CLI 退出码 | 耗时(s) | 轮数 | 工具调用 | 其中失败 | 独立复核 `go test` 退出码 |

没有协议或装配层错误。**这一步与上面的 6 次核心层运行是不同的代码路径**：CLI 走完整的

端点的「生效性」另有反向对照：只把 `base_url` 换成不可达地址，错误从移植前的

`[network] request failed: Post "http://127.0.0.1:1/v1/chat/completions": dial tcp ... connection refused`，
直接指向配置的端点。详见 [CFG-004 记录](CFG-004.md) 的「验证」一节。

**覆盖边界（以下都不能宣称）**：

- 第一次补充 6 次（A1–A3、B1–B3）验证的是 `pkg/` 核心层（agent 循环 + provider 协议解析 + builtin 工具），
  **不经过 `cmd/basework` 装配**：没有权限检查、没有会话持久化、没有后台 job、没有 TUI。
  这一缺口已由下面「产品层（CLI）路径」的 3 次运行补上（默认权限为 yolo，故权限交互仍未覆盖）。

  它证明的是协议适配正确，**不能**推广成"不同厂商模型的兼容性"。
