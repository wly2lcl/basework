# CFG-001 脱敏的有效配置解释

## 基线

- 看板：前置 BASE-001 已完成。
- 配置系统基线：`pkg/config` 为 CoW 配置（`Store` 原子指针交换），`Load(path)` = 默认值 ← JSON 文件覆盖 → `Validate`；`Discover()` 搜索顺序 = 当前目录 → 父目录逐级向上 → `~/.config/basework/config.json`。
- 环境覆盖基线（分散在 cmd 层，pkg/config 不管 env）：
  - `BASEWORK_PROVIDER` 覆盖 provider（`newRuntimeAgent` / `tui.go`）；
  - `BASEWORK_AUDIT_MODE` 选择审计模式（`runtimeAuditMode`）；
  - API key：配置字段优先（`providerAPIKey` 的 switch），否则走 `lookupAPIKey` 的环境变量链（opencode 有 OPENCODE_API_KEY → OG_API_KEY → OPENAI_API_KEY 三级回落）。
- 之前没有任何「解释当前配置」的入口：用户只能自己拼 Discover 顺序、默认值和环境覆盖。
- 缺口核对结果：`cmd/basework` 无 `config` 命令；`pkg/config` 无脱敏工具。

## 变更

新增文件：

- `pkg/config/redact.go`：递归脱敏视图。
  - `SensitiveKey(key)`：大小写不敏感的字段判定——含 secret/password/passwd/api_key/apikey/private_key/credential；等于 key 或 `*_key`；等于 token 或 `*_token`（`token_path` 这类「引用位置」**不脱**，保住排查价值）；等于 authorization 或 `*_authorization`。
  - `RedactedView(cfg)`：序列化为通用 map 后递归走 key、替换敏感字符串值为 `RedactionMarker`（不含长度/前缀等可猜测信息）。走通用 map 而非字段清单的原因：`MCPConfigs` 是任意嵌套的用户数据，字段清单式脱敏必然漏。空值原样保留——「未设置」是有用信息。返回全新结构，不改原对象。
- `pkg/config/redact_test.go`：4 条测试（判定规则正反例、8 个秘密值全不泄漏且非敏感值保留、不改原对象、脱敏不减字段）。
- `cmd/basework/config.go`：`basework config explain` 命令。
  - 输出：配置来源与解析顺序 → 环境覆盖（`BASEWORK_PROVIDER`/`BASEWORK_AUDIT_MODE`，与 runtime 同口径）→ 生效 provider/model → 各 provider 的 key 状态（**只报有无与来源，永不报值**）→ 脱敏后的完整有效配置 JSON。
  - key 来源判定 `apiKeySource`/`apiKeyEnvVars` 与 `providerAPIKey`/`lookupAPIKey` 同构（配置字段优先、环境变量链含 opencode 三级回落、copilot/ollama 无 key）。刻意不用 `provider.RequiresAPIKey`：它与 runtime 实际读 key 的行为不一致（bedrock/opencode 都会读），解释输出必须以 runtime 真实行为为准。
  - `renderConfigExplain(w io.Writer, ...)` 写入注入的 Writer，「秘密不出现在输出」可直接被测试断言。
  - 三条铁律写进文件头：只读、不发网络请求、秘密绝不进 stdout/stderr。
- `cmd/basework/config_explain_test.go`：3 条测试（秘密不泄漏+环境覆盖反映+只读哈希不变、文件不存在回退默认值、未设置时提示可用环境变量）。

修改文件：

- `cmd/basework/main.go`：注册 `configCmd`。

关键决策：

- 覆盖口径「与 runtime 相同」靠复用/同构实现保证，而不是重新发明：provider 覆盖读同一个 `BASEWORK_PROVIDER`；key 来源按 `providerAPIKey` 的取值路径判定。sync 约束已写成注释（新增 provider 两处一起改）。
- 脱敏标记统一为一个常量，不保留被脱敏值的任何统计特征。

## 剩余与交接

- 环境覆盖目前只有 provider 与 audit mode 两个入口（cmd 层各自读取），`pkg/config` 本身不做 env 合并；若未来覆盖项增多，应把 env 层下沉到 `pkg/config` 并让 explain 与 runtime 消费同一份「覆盖清单」——目前两处靠注释约定同步。
- `Validate` 的嵌套验证已覆盖 OAuth provider 必填项与端口范围（CFG-001 步骤 4 的「嵌套配置验证」以此为基线复核，未发现新缺口）；默认合并即 `Load` 的「默认值 ← 文件」语义，已被 Load 测试覆盖。
- CFG-002（可组合启动预设）依赖 CFG-001；CFG-003 是下一个可领取任务。
- 真实模型凭证不可用与本任务无关：explain 不依赖任何 provider 连接。

## 结论

CFG-001 完成。`basework config explain` 提供只读的有效配置解释：来源与解析顺序、与 runtime 同口径的环境覆盖、逐 provider 的 key 来源状态（只报有无）、经递归脱敏的完整有效值。测试样例中的秘密（含任意嵌套的 MCP env token）经验证不出现在 stdout/stderr；解释过程不改配置、不发网络请求。全部 28 项门禁命令通过，人工场景 4 项通过。
