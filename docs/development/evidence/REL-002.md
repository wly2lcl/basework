# REL-002 验证记录：模型能力与认证信息说明

## 基线

- 起点 HEAD：`935fde1`（*fix: make context replay deterministic*）；工作树含 REL-001 与
  BASE-001 的未提交改动（本轮继续在其上叠加）。
- 环境：macOS 26.6.2 arm64 / go1.26.0；`go` 需 `export PATH=/usr/local/go/bin:$PATH`。
- 相关既有实现：
  - `pkg/llm/model.go` 只有 `Model.Supports(cap) bool`，`false` 同时表示"不支持"与"没声明"。
  - `pkg/provider/compat.go:49` 与 `pkg/provider/openai.go:41` 对所有走 OpenAI 兼容路径的
    模型无条件声明 `CapVision=true`。
  - `cmd/basework/model.go` 的 `model list` 只有 Provider / Model ID / Free 三列。
- 复现的缺口（不是猜测，是代码事实）：
  - `openai-compat` 端点上的任意模型 ID（例如 `my-model`）被声明为支持图片输入；
    `deepseek-chat`、`llama-3.3-70b-versatile`、`Mixtral-8x7B` 这类纯文本模型同样被声明支持视觉。
  - "免费"与"需要 API key"混在同一个 `Free` 字段里表达。
  - 缺 key 时 `model use` 会照常改写配置，直到第一次真实请求才失败，且不提示替代方案。

## 变更

- 新增 `pkg/llm/capability.go`：`Support` 三态（`SupportUnknown` / `SupportUnsupported` /
  `SupportSupported`）、`CapabilitySource`（`declared` / `configured` / `probed`）、
  可选接口 `CapabilityReporter`、`DescribeCapability`、`CheckRequiredCapabilities`、
  `MissingCapabilityError`。
  关键语义：`Supports()` 返回 `false` 时 `DescribeCapability` 给出 `Unknown` 而不是
  `Unsupported`——`bool` 的 `false` 不构成"不支持"的证据。
- 新增 `pkg/provider/capabilities.go`：按 provider 元数据 + 模型家族给出能力结论。
  协议保证的能力（tools / streaming）标 `declared`；视觉能力按 `visionRules` 有序规则表
  匹配（更具体的例外排在前面，如 `grok-2-vision` 先于 `grok-2`、`o1-mini` 先于 `o1`），
  匹配不到就是 `Unknown`，不再猜测。同时导出 `CapabilitiesFor` / `RequiresAPIKey` /
  `APIKeyEnvVar` / `KnownProvider` / `SortedNames`。
- `pkg/provider/compat.go`、`pkg/provider/openai.go`：能力表由 `capabilitySet` 生成，
  视觉能力仅在结论为 `Supported` 时进入 `capabilities`；两个模型类型实现 `Capability()`。
- `cmd/basework/model.go`：
  - `model list` 增加 Tools / Streaming / Vision / API key 列，三态分别显示 `yes` / `no` / `unknown`。
  - 新增 `model info <id>`：逐项显示能力、来源、依据说明与 key 需求，unknown 项单独提示。
  - `model use` 在缺 key 时返回明确错误（含实际读取的环境变量名与免费模型替代建议），
    并且**不写入配置**——不静默换模型，也不留下一个跑不起来的配置。
- `cmd/basework/runtime.go`、`agent.go`、`tui.go`：运行入口做能力预检
  （`checkRuntimeCapabilities`，要求 tools + streaming），并在启动信息里展示能力摘要；
  结论全部已知时只在 `verbose` 下打印，存在 `unknown` 时始终提示。
- 行为变更（需注意）：`openai-compat` / `openai` 路径上的未知模型 ID 不再被声明支持视觉。
  `pkg/provider/compat_test.go:337` 原本断言 `Supports(CapVision)==true`，该断言固化的正是
  本任务要修的缺陷，已改为断言"未知模型不得被声明支持视觉"，并保留 tools / streaming /
  json_mode 的原有断言（收紧而非放宽）。

## 剩余与交接

- `probed` 来源尚无写入方：需要在真实请求后回写实测能力。归 REL-003（真实模型闭环）。
- 视觉家族规则表是人工维护的清单，新增模型家族时需要同步；未收录家族会如实显示 `unknown`，
  不会误报为支持。
- `RequiresAPIKey` 对 bedrock / copilot 返回 `false`（它们用 AWS 凭证 / OAuth token，不用 API key）。
  这两个 provider 当前不在 `model list` 的已知模型表里，因此不产生展示矛盾；
  若将来加入，需要把"需要凭证"与"需要 API key"进一步分开描述。
- `cmd/basework/onboard.go` 的引导流程尚未接入能力展示，属可选增强，不在本卡验收范围。

## 结论

验收项逐条对照：

| 验收条件 | 结果 | 依据 |
|---|---|---|
| 未知不伪装为支持 | 通过 | `visionRules` 未命中即 `Unknown`；`capabilities_test.go` 断言 unknown 模型不得为 supported；运行入口对 unknown 始终提示 |
| 免费与 requires_api_key 分离 | 通过 | `modelEntry.Free`（模型级）与 `requiresKey()`（协议级 + 免费标记）分别判断并分列展示；`TestModelEntryRequiresKeySeparatesFreeFromKey` |
| 不能通过静默禁用工具或擅自换模型来通过测试 | 通过 | 缺能力/缺 key 一律返回带替代方案的显式错误；`model use` 缺 key 时不改配置；无任何自动降级路径 |

针对性验证通过，新增 3 个测试文件覆盖全部验收条件，手工冒烟确认 CLI 输出与设计一致。
本任务不涉及真实网络请求，因此没有外部服务失败项。
