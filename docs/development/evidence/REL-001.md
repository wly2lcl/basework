## 变更

### 复现到的两个真实缺陷

**D1：增量事件携带累计值，与另一家 Provider 的方言冲突（参数重复拼接）**

`pkg/llm.ToolCallDelta.ArgsJSON` 在 `Complete=false` 时没有约定语义，三家 Provider 各说各话：

| Provider | `Complete=false` 时 `ArgsJSON` 的实际值 | 位置 |
|---|---|---|
| OpenAI / Ollama / Azure / Copilot / openai-compat | **累计值**（每次都带上前缀） | `pkg/provider/openai.go:486`（原文 `entry.ArgsJSON`） |
| Anthropic | **真增量**（`partial_json`） | `pkg/provider/anthropic.go:667` |
| Gemini | 不发增量，只发一次性完整参数 | `pkg/provider/gemini.go:474` |

而消费方 `pkg/agent/pipeline.go:147` 是**按增量拼接**的（`tc.argsJSON += evt.ToolCall.ArgsJSON`）。
对 OpenAI 系来说这条路径拼出来的是垃圾串，目前只因为 `Complete=true` 事件随后用完整值覆盖
（`pipeline.go:132-135`）才没暴露。真实流一旦缺少 Complete 事件，参数就是错的。

复现（加修复前）：`[]string{"", "{\"city\":", "{\"city\":\"Beijing\"", "{\"city\":\"Beijing\"}"}`
——后三段都在重复携带前缀。

**D2：多个工具调用的完成顺序不确定（ID 与结果可能错位）**

`parseOpenAIStream` 与 `Pipeline.callLLM` 的补齐逻辑都用 `for idx := range <map>` 遍历，
Go 的 map 迭代顺序随机。同一份响应因此会在不同运行中产生不同的工具调用顺序。

复现（加修复前，3 个交错到达的调用跑 100 轮）：

```
=== Complete 事件顺序分布（100 轮）===
  call_b,call_c,call_a -> 19
  call_c,call_a,call_b -> 19
  call_a,call_b,call_c -> 62
```

顺序随机会直接改变持久化的 assistant 消息，进而改变 `RequestFingerprint`
（`pkg/agent/request.go` 的请求指纹）——与本仓 `935fde1`「让上下文重放确定」的目标相抵触。

## 剩余与交接

未验证内容：

- **真实 Provider 端到端未验证**：本轮全部证据来自本地 `httptest` SSE 重放与 mock 模型，
  没有调用任何真实端点（相关环境变量均未设置）。各家线上流式行为与协议文档存在偏差的可能，
  由 REL-003 覆盖。
- **取消（cancel）路径未做流中取消的专项重放**：`parseOpenAIStream` 在 `ctx.Err() != nil` 时
  不发送 scanner 错误（`openai.go:524`），`Pipeline.callLLM` 在流后检查 `ctx.Err()` 并返回取消错误
  （`pipeline.go:159`），本轮未新增该路径的测试。
- **同一 index 出现两次 `Complete=true` 的重复执行风险未证伪**：现有 5 个 provider 都不会这样发，
  属消费方加固问题，不满足「只修复可复现的不一致」的范围约束，故未加投机性去重；
  若未来接入的 provider 可能重复发送完成事件，需要补 (Index,ID) 去重。
- 未使用真实文件型 job 或文件系统副作用来端到端证明「不重复执行」，只证明了协议层不会重发请求。

## 结论

- 是否满足任务卡全部验收：**满足**。
  1. 「参数不丢失也不重复拼接」——D1 已修复，增量事件只携带片段，拼接结果与完整参数逐字节相等；

     断流只补齐一次当前工具调用。

  确认能抓住回归。真实 Provider 与取消路径的边界已在上节写明，由 REL-003 与本卡后续跟踪，
  不影响本卡验收条件。
