## 变更

本轮实施范围：

1. 将源码最低 Go 版本升级至 `1.26.10`，使用已校验下载的 Go 1.26.10 工具链构建；不改本机全局 Go 默认设置。最终模块为 `x/net v0.60.0`、`x/text v0.42.0`、`x/image v0.45.0`、`goldmark v1.7.17`，连带更新 `x/sync v0.23.0`、`x/sys v0.48.0`。`x/net v0.60.0` 要求 `x/text v0.42.0`，因此选择该版本，而非仅达到漏洞最低修复版本 v0.41.0；`go mod tidy` 和 `go mod verify` 均已通过。
2. `make check-vuln` 调用 `scripts/check-vuln.sh source`，使用固定版本 `golang.org/x/vuln/cmd/govulncheck@v1.8.0`，依次扫描 `-test ./...` 与 `-test -tags=sqlite,memory ./...`。实际二进制使用同一脚本的 `binary` 模式；工具/漏洞库错误或漏洞命中均返回失败，不把 JSON 模式退出 0 当作无漏洞。
3. 重新编译声明的五平台二进制、扫描构建产物，并执行现有功能与工程回归。镜像包含的二进制必须绑定本轮构建。
4. 集中更新当前安装、贡献、验证、发布、安全和状态文档；历史证据保持原来的日期、候选与 Go 版本。

本轮验证结果与产物对应关系已保存到[脱敏 JSON](SEC-002-security-2026-10-23.json)，包括产品源码/模块摘要、7 个构建输入文件 SHA-256、五平台二进制与归档哈希、镜像 ID 与提取二进制哈希、OCI 哈希和各检查日志摘要。原始日志保留在本次本地临时工作目录，不作为唯一复现步骤；上方版本和下方仓库内入口可重新执行。

### 产物对应关系

- 五平台 snapshot 使用 `sqlite memory` tags；实际二进制与归档内 payload 哈希逐个相等。Windows amd64 和 macOS amd64 本轮只交叉构建/扫描，没有目标系统运行。
- 本机 `basework` 与 `bin/basework` 已替换为本轮 darwin/arm64 安全二进制，二者 SHA-256 均为 `71e354ad33c2161ac9089ee2482c0c73b37e3c35e5e03f70a55654cd8a900474`，原生 version/init/config Smoke 退出 0。
- Docker 由候选脚本独立构建 linux/amd64 与 linux/arm64 二进制，构建后先扫描，再构建 OCI 与两个本地单平台镜像；从最终镜像提取的实际二进制再次扫描无告警。因此镜像二进制的哈希不要求与 GoReleaser 归档相同，分别保留构建标识和哈希。
- 所有产物为未发布的 dirty 工作区候选，`vcs_modified=true`。GoReleaser、镜像和程序的 commit 字段仍为基线 `4283fef`，须结合脱敏 JSON 中源码、构建输入和产物哈希识别，不能宣称对应一个已提交的安全版本。

### 失败、修复与重试

- Docker 临时 builder 初次拉取构建镜像遇到 EOF；重试后成功。首次 amd64 Alpine 包源下载出现 TLS 失败；保持证书验证，重试后双架构构建成功。这些为网络型失败，没有通过跳过 TLS 校验或删除依赖来规避。
- Go 安全最低版本暴露 OPT-001 旧夹具固定 `GOTOOLCHAIN=local` 的兼容问题，已改为使用满足当前模块要求的工具链。随后发现宿主 Provider key 会使预期交互提示被跳过；PTY 环境会合并宿主环境，仅删除字典项不足以隔离，已显式覆盖为空值。最终复跑通过并退出 0；两处均为夹具修复，没有修改业务行为。
- 全部验证基于 `4283fef` 后的安全修复工作区；程序中的 commit 字段仍指基线，不能用这个字段冒充干净提交对应关系。本轮产物应结合工作区差异和哈希识别。
