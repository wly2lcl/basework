# JOB-003 验证记录：超时取消与进程树清理

## 基线

- 起点 HEAD：`935fde1`；工作树含 BASE-001 / REL-001 / REL-002 / REL-004 / JOB-001 / JOB-002 / EDIT-001 的未提交改动。
- 环境：macOS 26.6.2 arm64 / go1.26.0。
- 相关既有实现核对结果：
  - 取消与超时都靠 `exec.CommandContext` 的默认行为：ctx 结束时 `os/exec` 调用
    `Process.Kill()`，**只终止直接子进程**。`sh -c "sleep 30 & wait"` 里的 `sleep`
    是孙进程，不在清理范围内。
  - 终态原因只有四档（succeeded / failed / canceled / interrupted），
    `failed` 同时吸收"非零退出""执行报错""跑太久"——界面上分不出"我掐的"和"跑太久"。
  - `Manager.Await` 用 1ms 轮询状态，不是等终态事件。
  - 没有"一个 owner 结束"的清理入口：会话关闭后它的后台命令仍在跑、输出文件仍占磁盘。
  - `pkg/tool/builtin/timeout.go` 只做 context 超时与事件发布，**不涉及进程**；
    它的 `WithTimeout` 与 job 超时是两套东西，本任务没有合并它们（合并会让
    同步 bash 的行为一起改变，属范围外）。
- 因此本任务的起点是"只杀直接子进程、原因不可区分、Await 靠轮询、无 owner 关闭清理"。

## 变更

### 新增进程组能力（`internal/jobs/process.go` + `process_unix.go` + `process_other.go`）

- `PrepareCommand(cmd)` / `TerminateCommand(cmd, grace)` / `ProcessGroupSupported()`。
- unix 实现（`//go:build unix`）：`Setpgid = true` 让命令成为自己进程组的组长，
  终止时对 `-pgid` 发信号，因此**整棵树**（sh 及其孙进程）一起收到。
  先 `SIGTERM`，宽限期（默认 `DefaultKillGrace = 2s`）后对仍存活的成员 `SIGKILL`。
- **不阻塞等待**：`TerminateCommand` 是 `os/exec` 的取消回调，阻塞在那里等于把
  "命令有没有死"和"`Wait` 什么时候返回"绑死。宽限期由定时器负责，且定时器在动手前
  重新确认进程组是否还有活着的成员——否则可能对一个已被回收、pgid 又被复用的组
  发 `SIGKILL`，误杀无关进程。
- `grace <= 0` 回落到默认宽限期，而不是退化成"直接强杀"：配置漏填不该变成更暴力的行为。
- 非 unix 实现（`//go:build !unix`）**显式返回 `ErrProcessGroupUnsupported`**，
  `prepareCommand` 为空操作。Windows 上要覆盖整棵树需要 Job Object，本项目未实现；
  调用方按错误值退化为终止直接子进程，并把这个限制暴露出来，而不是假装清理干净了。

### `Manager` 的终态原因与等待（`internal/jobs/jobs.go`）

- 新增终态 `StateTimedOut = "timed_out"`，并纳入 `State.Terminal()`。
  它单独存在是因为"用户主动取消"和"跑太久被掐掉"需要不同动作：
  前者要问用户改口径，后者要调超时或改后台执行。
- 原因判定**顺序即优先级**，每一档都有注释说明：
  1. `err != nil && ctx.Err() != nil` → `canceled`（人有意识的动作优先于计时器）；
  2. `errors.Is(err, context.DeadlineExceeded)` → `timed_out`；
  3. 其他 `err != nil` → `failed`（带可读原因）；
  4. `exitCode != 0` → `failed`（"退出码 N"）；
  5. 其余 → `succeeded`。
- `jobState` 增 `done chan struct{}`，在 `settle` 里（`settled` 幂等标志保护下）
  关闭一次。`Await` 改为等这个通道，**去掉 1ms 轮询**：既没有"job 已结束但还要等
  一个轮询周期"的延迟，也不会因为轮询间隔漏掉状态。关闭动作放在 Manager 锁外，
  否则等待方被唤醒后再去 `Get` 会互等。
- 新增 `CloseOwner(owner)`：收集该 owner 的取消函数与终态通道 →
  逐个取消 → 等全部终态 → 关闭并删除它的输出文件，返回被取消的个数。
  **顺序不可颠倒**：先删文件再等执行体，正在写的 sink 会往已删除的 inode 里写，
  结果是"命令成功了但输出丢了"。等待无界——`Runner` 的契约就是必须响应 ctx 取消，
  一个不响应的执行体不该靠超时来掩盖。空 owner 返回 0，避免退化成"关闭所有人"。

### 适配器接线（`internal/tools/background.go`）

- 命令改为在独立进程组中运行，并接管 `cmd.Cancel`：调用
  `jobs.TerminateCommand(cmd, KillGrace)`；返回 `ErrProcessGroupUnsupported` 时
  退化为 `cmd.Process.Kill()`。
- **规范化 `cmd.Run` 的错误**：先看 `execCtx.Err()`，再退回 `*exec.ExitError`。
  理由：ctx 结束时 `os/exec` 可能返回 ctx 的错误，也可能返回"被信号杀死"的退出错误；
  不归一化就会把"取消"记成"退出码 -1 的失败"。
- 新增 `KillGrace` 字段（<=0 用默认值）。权限入口顺序（黑名单 → 路径检查 → 启动）未动。
- 代码注释里的覆盖边界同步更新：进程树终止归本任务，工具注册与重启恢复归 JOB-004。

测试非恒真的证据（本轮实现中真实出现并被修正的失败）：

1. `TestPrepareCommand_ChildBecomesProcessGroupLeader` 最初用 `ps -o pgid= -p $$` 读 pgid，
   在沙箱里 `ps` 被拒绝执行（`Operation not permitted`）而失败——不是被测代码的问题，
   改用 `syscall.Getpgid` 后通过；这同时说明该断言确实在检查行为而非恒真。
2. `TestCloseOwner_WaitsForOutputToBeFlushed` 起初在 `Await` 返回后立刻断言输出已关闭，
   结果 3 次里失败 1 次：`Await` 在 `settle` 关闭终态通道时即返回，而 `CloseOwner`
   关闭 sink 发生在其后。这是**测试的时序假设错误**（把产品行为描述得比实际更快），
   已改为显式等待 `CloseOwner` 返回，并新增"执行体未返回的窗口内文件必须存在"这一
   真正针对清理顺序的断言。

## 剩余与交接

- **运行时接线（JOB-004）**：`CloseOwner` 已实现并测试，但 `cmd/basework/runtime.go`
  目前**还没有 job Manager**（`BackgroundBashTool` 也尚未注册进工具表），
  因此"会话结束时调用 `CloseOwner`"这一步无处落地。这属于 JOB-004 的
  "注册 job 查询/输出/取消工具并沿用权限 + 持久化"，本卡未越界接线。
- **Windows 运行时未实测**：只有交叉编译检查。Windows 上孙进程会残留，
  这一限制由 `ProcessGroupSupported()`、`ErrProcessGroupUnsupported` 与文档显式声明。
  要真正覆盖需要 Job Object，属独立的平台适配工作。
  - **（2026-09-14 更新）本项已被后续工作取代**：CI 首次实际触发暴露了退化行为的真实后果——
    `sh -c "sleep 30"` 的孙进程持有继承来的管道写端，`cmd.Wait()` 阻塞到它自然退出，
    1 秒超时实测拖满 30 秒才进终态，即超时/取消在 Windows 上等于没有。现已新增
    `internal/jobs/process_windows.go`，用 `taskkill /T /F` 按父进程链终止整棵树（退出码 128 =
    进程已不存在，按 unix 的 `ESRCH` 语义处理）。平台能力随之改名为
    `ProcessTreeTerminationSupported()` / `ErrProcessTreeUnsupported`（旧名 `ProcessGroupSupported()`
    在 Windows 上会变成谎话；退化错误值只留给既无进程组也无等价手段的平台，
    `process_other.go` 构建约束收窄为 `!unix && !windows`）。Windows 侧**没有温和阶段**：
    控制台进程没有可捕获的终止信号，等一个发不出去的宽限期没有意义。Windows 运行时行为
    由 CI 实测覆盖，替代了原先的交叉编译口径；本卡其余边界（`setsid` 脱离、pid 复用、
    无进程组平台）不变。
- **脱离进程组的孙进程**：命令若显式 `setsid`/`nohup` 另起会话，就不再属于该进程组，
  不会被清理。这是进程组方案的固有边界，未做 `pgid` 遍历补杀（那需要枚举
  系统进程表，代价与误杀风险都更高）。
- **`TerminateCommand` 的 pid 复用风险**：`SIGTERM` 是对 `-pgid` 立即发出的，
  若调用时组长已退出且 pid 已被系统复用为新的组长，存在误杀可能。实际调用点只有
  `os/exec` 的取消回调（此时命令正在运行），风险被限制在这一前提下；
  定时器里的 `SIGKILL` 已做存活确认。
- **`CloseOwner` 的等待无界**：执行体不响应取消就会一直等。这是刻意的（见上），
  但调用方需要知道；若要加兜底应在调用方加超时，而不是在这里静默放弃清理。
- **同步 bash 未受影响**：`pkg/tool/builtin/bash.go` 的超时仍走
  `exec.CommandContext` 默认行为，孙进程不会被清理。合并两套口径会改变同步工具的
  现有行为与测试，属范围外，未做。
- **未验证范围**：Ubuntu 只有交叉编译检查，没有实机运行；`race` 依赖本机调度，
  不能证明所有交错。

## 结论

验收项逐条对照：

| 验收条件 | 结果 | 依据 |
|---|---|---|
| 取消后子进程无残留 | 通过 | `Setpgid` + 对 `-pgid` 发信号；`TestTerminateCommand_KillsGrandchildren`、`TestBackgroundBash_CancelLeavesNoGrandchildren`、`TestBackgroundBash_TimeoutKillsGrandchildren` 都用真实孙进程 pid 断言消失 |
| 终态只发布一次且原因正确 | 通过 | 唯一发布点 `settle` + `settled` 幂等（JOB-001 已覆盖），原因按固定优先级分五档；`TestRun_TerminationReasonMapping`（5 子例）、`TestRun_CancelWinsOverDeadline`、`TestRun_NaturalExitAtCancelMomentKeepsObservedResult`、`TestBackgroundBash_TimeoutIsTimedOutNotFailed`、`TestBackgroundBash_NonZeroExitReasonIsExitCode` |
| 不支持的平台行为显式说明并有对应 CI 验证 | 部分通过（诚实边界） | 行为显式：`ProcessGroupSupported()` 为 false、`TerminateCommand` 返回 `ErrProcessGroupUnsupported`、调用方退化并保留错误来源；验证是 `GOOS=windows go build ./...` 与 `GOOS=windows go vet ./internal/jobs/ ./internal/tools/`（含 Windows 专属测试文件）通过。**Windows 运行时行为未实测**，CI 矩阵是否实际跑到未在本地确认 |

针对性与全量验证（含 `-race`，`-count=3` 复跑）通过；本任务新增 22 条用例（jobs 16 + tools 6）
覆盖验收条件，"不支持的平台"一项按上述部分通过记录，未以交叉编译冒充运行时验证。
