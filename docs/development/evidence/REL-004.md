# REL-004 验证记录：请求审计运行时策略

## 基线

- 起点 HEAD：`935fde1`；工作树含 BASE-001 / REL-001 的未提交改动。
- 环境：macOS 26.6.2 arm64 / go1.26.0。
- 相关既有实现与缺口：
  - `pkg/agent/pipeline.go` 的 `recordRequestBuilt` 无返回值：编码失败、落盘失败都只
    `log.Printf` 后继续，然后照常调用 `Model().Stream`。
  - 后果是「日志里没有某条 `request.built`」有两种无法分辨的解释：那次请求没被记录，
    或那次请求根本没发出。压缩与磁盘故障都会制造这种缺失，不是理论问题。
  - `agent.CheckRequestInvariant` 存在但只供测试使用；按 Seq 截断重建的做法只写在
    `pkg/agent/request_invariant_test.go` 里，没有可复用的运行时 API。
  - `TurnD` 是导出接口，给它加必选方法会破坏所有外部实现。
- 卡片指出的既有边界：`system.prompt_set` / `steered` 写入失败已会阻断本轮调用并保留
  可重试状态；本卡要覆盖的是 `request.built` 的严格策略与重建失败路径。

## 变更

- 新增 `pkg/agent/audit.go`：
  - `AuditMode`：`compatible`（默认，写入失败只记日志继续）与 `strict`（发出任何
    Provider 调用之前中断）。`Normalize()` 把零值归一到 compatible，`Valid()` 拒绝未知取值。
  - `AuditPolicyProvider`：**可选**接口，从 `TurnD` 取策略。未实现即 compatible，
    因此既有嵌入实现行为不变（这是"旧嵌入调用保持兼容"的落点）。
  - `AuditError`：带 `Stage`（`encode` / `persist` / `rebuild`）、`Source`、`SessionID`，
    `IsAuditError` 与 `errors.As` 可判定。
  - `AuditBoundaries()`：把审计边界写成可断言的数据结构——
    事件日志投影（覆盖且可重建）、hook 改写（覆盖但**不可重建**）、
    工具定义快照（覆盖但**不可重建**）、Provider 传输变换（**不覆盖**）、
    助手回复与工具结果（不覆盖，且必须把日志截回请求那一刻）。
  - 运行时核对 API：`RebuildRequestAt(events, seq)`、`VerifyRequestBuilt(events, seq, tools)`、
    `RequestBuiltSeqs(events)`。
- `pkg/agent/pipeline.go`：`recordRequestBuilt` 改为返回 `*AuditError`；`callLLM` 按
  `auditMode()` 决定继续还是中断（中断时先 `RunAfterLLM(nil, err)` 再返回）。
  新增 `Pipeline.auditMode()`，未实现可选接口即回落 compatible。
- `pkg/agent/option.go`：`WithAuditMode(mode)` 与 `config.auditMode`。
- `pkg/agent/loop.go`：`agentTurnD.AuditMode()` 实现可选接口。
- `cmd/basework/runtime.go`：`BASEWORK_AUDIT_MODE=strict` 接入严格模式；取值非法时明确
  报错而非静默回落。
- 新增 `docs/adr/0005-request-audit-strict-mode.md`，固定两种模式、边界表与后果。
- 文档同步：`docs/ARCHITECTURE.md`（去掉"严格审计是未来任务"的过时表述）、
  `docs/reference/pkg/agent.md`（请求审计与 Known Limitations 两处）、
  `docs/STATUS.md`（请求来源与指纹一行）。

新增测试 `pkg/agent/audit_test.go`（11 条）：

| 测试 | 覆盖的验收点 |
|---|---|
| `TestStrictAudit_WriteFailureBlocksProviderCall` | 严格模式写失败 → **模型调用次数 0**；错误带 `Stage=persist`、`Source=request.built` |
| `TestCompatibleAudit_WriteFailureStillCallsProvider` | 默认模式写失败 → 仍调用 1 次，不中断 |
| `TestAuditMode_Normalize` | 零值 → compatible；未知取值不合法 |
| `TestAuditPolicyProvider_AbsentMeansCompatible` | 未实现可选接口的实现方按旧行为工作 |
| `TestVerifyRequestBuilt_PassesAtEachRequestsOwnSeq` | 两轮请求各按自己的 Seq 核对通过；并断言**最终日志重建的指纹与第一条请求不同**——即不能用最终日志代替当时快照 |
| `TestVerifyRequestBuilt_DetectsHookRewrite` | hook 改写 → 重建报"消息条数不一致"，固定 hook 属边界外 |
| `TestVerifyRequestBuilt_DetectsToolCountDrift` | 传入不同工具定义 → 报"工具定义条数不一致"，说明工具快照在日志之外 |
| `TestVerifyRequestBuilt_MissingSeq` | 缺少对应 Seq → 明确失败且错误含该 Seq |
| `TestAuditBoundaries_DeclaresUnreproducibleParts` | 守住边界声明：hook / 工具为"覆盖但不可重建"、Provider 传输为"不覆盖" |
| `TestRequestBuilt_WrittenOncePerAttemptInOrder` | 失败的那次请求也留痕；两次请求 Seq 严格递增，不合并 |
| `TestStrictAudit_CanceledContextStillLeavesAuditRecord` | 取消时序：审计记录先于那次未完成的调用写入 |

覆盖边界（已实际验证，不含推测）：
- 压缩时序（`compacted` 先于 `request.built`）由既有
  `pkg/agent/context_persistence_test.go` 的 Seq 断言覆盖，本次未重复造测试。
- 日志写失败用注入故障的 Store 复现，未在真实磁盘满条件下验证。
- 平台差异：三处 `log.Printf` 行为与平台无关。

全量门禁：见 `## 结论`。

## 剩余与交接

- `probed` 无关；但严格模式目前只有 CLI 环境变量入口，没有配置文件字段。
  若后续 CFG-001（有效配置解释）要展示它，应把 `BASEWORK_AUDIT_MODE` 纳入配置来源说明。
- `VerifyRequestBuilt` 尚未接到 `basework` 的任何诊断子命令上；CTX-002 / CTX-003 需要
  "按 Seq 重建请求"时可以复用现有 API，不需要重新实现。
- 严格模式下审计失败会中断对话：这是刻意的可用性取舍，已在 ADR 0005 记录。
  若将来要按会话粒度配置，需要新增配置字段而不改变默认值。
- `runlist` 未覆盖：`recordRequestBuilt` 的编码失败分支（`stage=encode`）没有单独的测试，
  因为它需要构造无法 JSON 序列化的消息，而 `ChatMessage` 全是字符串与切片；
  该分支由类型系统保证不可达，代码中已注明。

## 结论

验收项逐条对照：

| 验收条件 | 结果 | 依据 |
|---|---|---|
| 旧嵌入调用保持兼容 | 通过 | 策略经可选接口获取，未实现即 compatible；`WithAuditMode` 未调用时零值归一为 compatible；`TestAuditPolicyProvider_AbsentMeansCompatible` 与 `TestCompatibleAudit_WriteFailureStillCallsProvider` |
| 严格模式写失败时模型调用次数为 0 | 通过 | `TestStrictAudit_WriteFailureBlocksProviderCall` 断言 `streamCalls == 0` 且返回 `AuditError` |
| 能够按请求发生时的 Seq 重建并验证，不能用最终日志代替当时快照 | 通过 | `RebuildRequestAt` / `VerifyRequestBuilt`；`TestVerifyRequestBuilt_PassesAtEachRequestsOwnSeq` 显式断言最终日志重建的指纹与第一条请求不同 |

针对性验证通过；11 条新测试覆盖全部验收条件与卡片要求的四类时序（写失败、hook 改写、
取消、重试）；压缩时序沿用既有断言。本任务无外部服务依赖，失败项为 0。
